# v3 两屏那 7 条差异：实测结论（第 2042 轮）

> 你的推测是「主界面没认出这是 v3 工作区，于是继续走 v2 画布那条路」。
> **实测不成立** —— 原因不是同一处。证据如下。

## 一、架构值是对的

用 `DIAG_BODIES=1` 抓 2xx 响应体（新加的诊断开关）：

```
200 /api/project/architecture?hilo_workspace=7c7357ff… → {"projectArchitecture":"resource_v3"}
200 /api/project/architecture?hilo_workspace=54b19402… → {"projectArchitecture":"resource_v3"}
```

**网关答对了，渲染层也收到了。** 而且分支代码是对的：

```js
// workspace-canvas-area.jsx:103
architecture.data === "legacy"      ? <LegacyCanvasArea {...props} />
: architecture.data === "resource_v3" ? <WorkspaceV3Workbench {...props} />
: null
```

`useWorkspaceProjectArchitecture` 用 `loadWorkspaceProjectArchitecture` 校验
`projectArchitecture` 字段后返回，映射也没问题。

## 二、`/api/canvas/nodes` 不是画布发的，是聊天面板的 ComfyUI hook

```
app/renderer/src/chat/use-local-comfy-ui-workflows.js:114
  loadJson(`${API_PATHS.canvas}/nodes?type=file&limit=100`)
```

- `API_PATHS.canvas` = `"/api/canvas"`（`infra/workspace-gateway.js:234`）
- 拼出来正是 `GET /api/canvas/nodes?type=file&limit=100` —— **与差异里的那条完全一致**
- 该 hook 由 `chat/message-input-base.jsx:704` 调用（输入框里选择 ComfyUI 工作流用）
- **这个 `refresh()` 没有任何架构判断**，v3 工作区照样去拉 v2 画布节点 → 403 `PROJECT_ARCHITECTURE_UNSUPPORTED`

**所以这不是「走错渲染路径」，而是「一个与画布无关的 ComfyUI 列表功能，在 v3 工作区里调了 v2 接口」。**

## 三、7 条差异其实是三个独立原因

| # | 差异 | 真实原因 |
|---|---|---|
| 1 | `net.oursOnly: GET /api/canvas/nodes`（两屏都有） | `use-local-comfy-ui-workflows` 无架构守卫（上面第二节） |
| 2 | `dom.refOnly: workspace.structure-views / -canvas-tab / -list-tab、canvas.toolbar-project-assets` | 参照渲染结构视图，我们没有 —— 就是 78 个缺失 id 里的 4 个 |
| 3 | `ws.refOnly: editor_subscribe`（仅 ws-a-v3） | v3 工作台会订阅编辑器事件，我们没订阅 |

**三条互不相同，修一处不会消掉其余。**

## 四、为什么退出码是 1（按你的口径复核）

1. **未登记的集合差异**：4 dom + 1 net + 1 ws = 6（ws-a-v3）、1 net = 1（ws-a-v3-resource）
2. **这两屏没有像素护栏**：`residual-budget.json` 无条目 → `budget` 为 `null` →
   只要有一个非 AA 像素不同就判失败

**你说的“41 条 domDiff 只出报告、不参与判定”也对**：我上一轮把位置对比当成了失败原因，是错的。

## 五、修的顺序建议

1. **给 `use-local-comfy-ui-workflows` 加架构守卫**（只在 `legacy` 工作区拉 v2 节点）——
   这条最独立，一处改动消掉两屏的 net 差异；顺带呼应改动清单 #3（隐藏 ComfyUI）
2. `workspace.structure-*` 四个 id：补结构视图（工作量大，属 78 个缺失 id 的主体）
3. `editor_subscribe`：查参照在什么时候订阅，补上

**7 条差异一起修完之后**，才是给这两屏跑 5 次全量、生成护栏、状态标 `pending` 的时机。
