# 重要：界面门禁的黄金基准是 4.0.0，不是 4.0.3

## 证据

`~/ov-golden-ref/baseline-source.json`：

```json
{
  "mode": "reference",
  "recordedAt": "2026-10-22T01:14:53.448Z",
  "referenceVersion": "4.0.0",
  "mainScript": "app://./assets/index-BBp4hclA.js"
}
```

`index-BBp4hclA.js` 正是 **4.0.0** 的主 bundle（4.0.3 的是 `index-B3Ss5vz1.js`）。

## 这意味着什么

1. **门禁比的是「我们 vs 4.0.0」，而我们在还原 4.0.3。**
   两者方向相反：把源码改得更像 4.0.3，就会**离 4.0.0 更远**。

2. **像素平均值持续上升是预期的，不是退步。**
   2.5361%（无 4.0.3 CSS）→ 2.5459% → 2.5505% → 2.595%。
   每加一份 4.0.3 的样式/组件，数值就往上走一点 —— 因为参照物是旧的。

3. **「7 屏失败」不是缺陷清单，而是「4.0.3 与 4.0.0 的差异清单」。**
   例：`connectors-category-all` / `plugins-tab-*` / `connectors-sort` 等 6 个 id
   **在 4.0.3 的 bundle 里一个都搜不到**，但门禁报 `refOnly`。
   原因：这些 id 存在于 **4.0.0** 的 DOM 里，4.0.3 把它们去掉了/改名了。
   所以"我们缺它们"其实说明**我们正确地跟随了 4.0.3**。

4. **反过来说，`oursOnly` 的项（如 `canvas.node-promote-to-asset`）
   可能是 4.0.3 新增的**，我们做对了，却被记为差异。

## 因此

- **不要再为了压低这个数字去改源码。** 那会让我们离 4.0.3 更远。
- 若要用门禁验证 4.0.3 还原，正确做法是**重新录制 4.0.3 的黄金基准**
  （把 `.probe/reference/4.0.3` 跑起来录一份 `baseline-source.json` +
  dom/mask/net/png），然后把门禁指向新基准。
- 在那之前，门禁的数字只能当作「我们相对 4.0.0 漂移了多少」来读，
  不能当作「4.0.3 还原完成度」。

## 这条结论修正了本会话中的多个判断

- 第 50 轮「补 CSS 反而让差异变大」—— 正常，因为 CSS 是 4.0.3 的
- 第 92 轮「源码保真度与像素相似度背离」—— 根因就在这里
- 第 95 轮「照抄 gap-1 更差」—— 4.0.3 的间距配 4.0.0 的基准，当然更差
- 第 122~126 轮「7 屏失败是登记差异」—— 是 **4.0.3 与 4.0.0 的版本差异**
