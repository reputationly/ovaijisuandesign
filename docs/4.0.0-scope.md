## 七、一条重要的夹具限制：**单屏数字不可与全量比**

第 233 轮实测：

| 跑法 | `ws-canvas-ops` |
|---|---|
| 全量 40 屏 | **0.142%** |
| 只跑 5 屏（`ONLY=ws-canvas-ops,…`） | **4.055%** |

差 30 倍。原因是这些工作区屏依赖**前面屏留下的状态**（登录、workspace fixture、资源准备），
单独跑时准备不全，差异自然大。

**结论：只有全量 40 屏的数字可比。**
以后验证改动，不要用 `ONLY=<工作区屏>` 的结果下判断——
要么跑全量，要么用 `ONLY=home`（首页不依赖前置状态）。

这一条也解释了第 232 轮我为什么误判「常量改动引入回归」：
我用单屏结果否定了正确的改动，回退后单屏变成 3.69%，反而更差；
再跑全量才确认新值是对的（0.142%，与改动前 0.113% 的差在噪声内）。

## 八、工具坑：**Python 的字符索引 ≠ JS 的 UTF-16 索引**

第 234 轮查 `failure` / `notify` 是不是真顶层声明时，我用 Python 切片验证偏移，得到
「偏移错位」的结论。**这个结论是错的。**

```
Python len(s)              = 21,994,684   （字符数）
UTF-16 码元数               = 21,994,968   （JS 的 string 索引）
非 BMP 字符（emoji）        = 284
grep "^function failure"   = 能匹配
```

**284 个 emoji** 让 Python 的字符索引比 JS 的码元索引少 284，
于是从第一个 emoji 之后，所有偏移都错开。

用 Node 复核：

```
failure 17770970 → "function failure(id2, code2) {\n  return { type: \"f"
notify  17770856 → "function notify(callback) {\n  try {\n    void Promi"
```

**偏移是对的。** `failure` / `notify` / `storage` / `owners` / `ready` / `workspaces`
确实是 bundle 里的**真实顶层声明**，只是名字太通用、来自还没还原的模块。

### 影响

- 所有取回工具（`extract-from-chunk.mjs`、`build-toplevel.mjs`、`check-constants.mjs`、
  `chunk-coverage.mjs`）都是 **JS 写的**，索引正确，不受影响；
- 只有我用 Python 临时核对时会被误导。

**以后核对偏移一律用 Node，不要用 Python。**

## 九、`--nwh` 是**收敛**的（与 `--shell` 相反）

第 235 轮用「迭代补入」测 `--nwh`：

```
圈 1: 清单 48 个 → 未绑定 76 → 补入 67
圈 2: 清单 115 个 → 未绑定 1 → 补入 0
```

**2 圈收敛，115 个声明就够。** 数据见 `scripts/v3preload/nwh-closure-measurement.json`。

这和 `--shell`（8 圈 80 → 2,292，不收敛）形成明确对照：

| 模块 | 圈数 | 结果 |
|---|---|---|
| `--task` | — | 3 个声明，已闭合 |
| `--chatad` | — | 1 个，已闭合 |
| `--resource` | — | 5 个（余 2 个 react-query 内部） |
| **`--nwh`** | **2 圈** | **115 个，收敛** |
| `--shell` | 8 圈 | 2,292 个，发散 |

### 它卡在哪

不是闭包，是**合并 import**：

取回的片段本身带着 bundle 的 import 语句，例如

```js
import { …, r as reactExports, … } from "./index-Dd7owO9f.js";
```

与文件头自己写的 `import reactExports from "react"` 冲突。
而我上一版**整体剥离所有 import**，又让片段依赖的模块丢失，未绑定从 1 涨到 475。

**正确做法**：逐片段解析 import，按模块路径合并去重，
把 `r as reactExports` 这类改名映射到我们自己的 import。

这是一件明确、有边的活，但需要单独一轮。

### 因此 `native-workbench-host.jsx` 的 3 处缺口是**可还原**的

之前判断「卡在 DI 服务」不准确 —— `INativeWorkbenchService` /
`IRendererPersistenceMainService` 都在 115 个声明里，只需正确合并 import。

## 十一、更正：`--nwh` **不可还原**（第 237 轮修正上两轮的判断）

### 我上两轮说错了两次

- 第 235 轮：说「nwh 2 圈收敛（48→115），可还原，卡的只是 import 合并」；
- 第 236 轮：取回 11 个 DI 令牌（66 行），以为补上了缺口。

**都不对。** 这轮真正去改 import 才发现：

```
从 use-window-chrome chunk 引入的名字：约 300 个
能解析回树内的：                        9 个
无法解析：                            291 个
```

样本：

```
createGroupNodeId   useTranslation   cn$1   Button$1   cva
I18nContext         getI18n          warnOnce        isString$1
```

这些名字在**整棵树里都没有导出** —— 它们来自 `use-window-chrome-DbNyfMCt.js`，
一个 **28.4% 覆盖率的共享 chunk**（799 声明）。

### 所以 nwh 的性质和导出引擎一样

| 模块 | 闭包 | 真正的阻塞 |
|---|---|---|
| 导出引擎 | 发散到 60k | 共享 chunk `index-Dr87oCf8` |
| **`--nwh`** | **收敛（115）** | **共享 chunk `use-window-chrome`（291 个不能用）** |
| `--shell` | 发散（2,292） | 同上 |

**闭包收敛 ≠ 可还原。** 还要看它依赖的 chunk 在树里有没有。

### 修正后的判定规则

```bash
node scripts/v3preload/closure-plan.mjs --<mode>     # 第一步：看是否递减
node scripts/v3preload/gen-imports.mjs <未绑定名…>   # 第二步：看能否解析到树内
```

- 递减 **且** 未绑定名能解析 → 做；
- 递减但大量名字解析不到 → **仍然不可做**（这次就栽在这）。

`workspace/main-services.js`（66 行 DI 令牌）和 `resolve-chunk-imports.mjs`（915 条别名表）
都是**正确的、可复用的**资产 —— 只是不足以让 nwh 整体接上。
