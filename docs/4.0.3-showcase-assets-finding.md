# 首页封面请求（showcase-assets）：答案

## 问题（此前未解）

> 首页封面请求用 `setBlockedURLs` 和 `Fetch` 都拦不住，到现在还不知道请求是从哪里发出去的。

## 答案（第 2046 轮，用 Playwright `route` 分别在两侧实测）

用同一个探针，分别以 `PROBE_UI=recovered`（我方界面）与 `PROBE_UI=reference`（4.0.3 参照界面）启动应用：

| 指标 | 我方（recovered） | 参照（reference） |
|---|---|---|
| `route` 拦 `/api/v1/home/showcase-assets/**` 命中数 | **r1=4 / r2=8 / home=22** | **0 / 0 / 0** |
| 请求总数（skills-connectors） | 70 / 68 | 90 / 85 |
| `/api/plugins` 响应体 | `{"plugins":[]}` | `{"plugins":[]}` |

**结论有两条：**

1. **`route` 确实能拦住这些请求** —— 所以「拦不住」是门禁侧
   （`Fetch` + `setBlockedURLs`）的用法问题，不是请求来自别处。
2. **参照界面根本不发这些请求** —— 22 次命中全部来自我方。

**也就是说：`showcase-assets` 是我方多出来的请求，4.0.3 的首页没有它。**

这与门禁里看到的 `net::ERR_ABORTED`（8 条，全部是 showcase-assets）对得上：
我方先发起、随后又被取消，而参照连发起都没有。

## 下一步

- 查我方首页在什么条件下请求 `showcase-assets`（对照参照为何不发）
- 若确认是多余请求，移除后既减少噪声，也可能消掉首页那 14.72% 里的封面差异

## 第 2047 轮：进一步定位

- `showcase-assets` 这个**路径在参照里完全不存在**（720 个文件搜 0 命中）；
  我方只在 `generation/use-skill-categories.js:128` 出现，且那是一处 **URL 白名单过滤**，
  不是构造请求的地方 —— 说明 URL 来自**服务端下发的配置**。
- 两侧都会请求 `GET /api/v1/apollo/config?key=home_tabs_showcase_config`
  （参照的 home chunk `index-BiM9K7Hw.js` 里也有 `home_tabs_showcase` 这个键）。
- 我方在 `home/data.js:287` 读这个配置并按 `showcase-assets/...` 取图；
  参照读同一个键但**不产生这类请求**。

**结论：同一个配置键，两侧消费的字段不同。** 我方从里面取 `showcase-assets` 图片地址，
参照不取（或取了不用）。

**下一步**：对比 `home/data.js` 对配置的解析与参照的解析，
找出参照实际使用的字段 —— 这既解释了多余请求，也很可能就是首页那 14.72% 里封面差异的来源。

## 第 2048 轮：找到字段差异的直接证据

- 我方 `home/data.js` **完全没有** `showcase-assets` / `coverImage` / `cover` 引用
  → 说明 `showcase-assets/...` 的 URL 是**配置数据里原样带来的**，
  我方只是用 `generation/use-skill-categories.js:128` 那处做 URL 白名单校验后直接使用。
- 参照 home chunk 里：
  `coverImage` **0** 次、`showcase-assets` **0** 次、`imageUrl` **0** 次，
  **`coverUrl` 3 次**。
- 我方 `coverUrl` 只出现在 `settings/feature-popup.jsx`（与本议题无关）。

**结论：参照用 `coverUrl` 渲染封面，我方用配置里的 `showcase-assets` 路径渲染。**

**这就是「同一个配置键、消费字段不同」的具体所指，也解释了为什么只有我方发出 22 次
`showcase-assets` 请求。**

**下一步**：在首页封面渲染处改用 `coverUrl`（或与参照一致的字段），
预期既能去掉多余请求，也能缩小首页那 14.72% 的封面差异。

## 第 2053 轮：三层配置都没有图片 —— 结论定案

`home_skill_showcase_config` 的响应（172 字节，200）：

```json
{ "schema_version": 1, "enabled": true, "default_secondary_id": "all",
  "secondary_categories": [
    { "id": "all", "title": {"zh":"全部"}, "query": { "source": "official-featured" } }
  ] }
```

**也没有图片字段** —— 它只描述「有哪些二级分类、每类用什么 query 去查」。

三层配置（tabs / skill / project）全部看完，**都没有图片 URL**。

### 定案

**`showcase-assets/...` 的 URL 不在配置里，而在 provider 查回来的「数据条目」里**
（即 skill market / 项目列表的每一项）。

- **我方**：渲染卡片时用条目里的图片字段，值形如 `/api/v1/home/showcase-assets/<hash>-<hash>`
- **参照**：`showcase-assets` 在 720 个参照文件里 **0 命中** → 它从不用这种 URL，
  而是用条目里的另一个字段（其 bundle 里 `coverUrl` 出现 3 次）

**所以差异的最终形态是：同一份数据条目，两侧取的不是同一个图片字段。**

### 可执行的下一步（具体到改哪里）

1. 抓 `home_skill_showcase_config` 里那个 query（`source=official-featured`）对应的**数据响应**，
   看每个条目里有哪些图片字段（预计同时有 `coverUrl` 与 `showcase-assets` 形态）
2. 在首页卡片渲染处改用参照那个字段
3. 预期效果：22 次多余取图消失 + 首页封面差异缩小

## 第 2056 轮：决定性数据 —— 全是 `<img>` 发出的

给探针加了一条 `page.on("request")`，按 `resourceType()` 统计这些请求：

```
8x  image @ app://./skills
22x image @ app://./
```

**30 次全部是 `image` 资源类型 —— 也就是由 `<img src="...">` 发起的，不是 fetch/XHR。**

### 这条数据的含义

1. URL 一定来自某个 `<img>` 的 `src`，而 `src` 的值来自**数据里的某个字段**
   （我们代码里 `home/media-showcase.jsx:103/123` 用的就是 `item.coverUrl`）。
2. 我方 `normalizeHomeQuickStartAssetUrl` 只放行
   `pathname` 以 `/api/v1/home/showcase-assets/` 开头的 URL ——
   **说明数据里 `coverUrl` 这类字段的值本身就是 `/api/v1/home/showcase-assets/...`**。
3. `/skills` 那 8 次说明它不只是首页——技能卡片也在用同类字段取图。

### 仍未解释的（我把范围收窄到这里）

**既然两侧读同一批数据、都用 `<img src={coverUrl}>`，为什么参照一个请求都不发？**

两种可能，需要一次实测来区分：
- **A.** 参照拿到的数据里，这些字段不是 `showcase-assets/...`（例如是 CDN 地址）
- **B.** 参照根本不渲染这些 `<img>`（懒加载/条件不满足/走了别的组件）

**区分方法**：参照侧同样记录「所有 `<img>` 的 src 前 60 字符」，
看它到底渲染了哪些图片地址。这一步能一次分开 A 与 B。

**我已在这条上错了两次（字段归因），所以这次不再推断，只写清「下一步用什么实测来分开」。**
