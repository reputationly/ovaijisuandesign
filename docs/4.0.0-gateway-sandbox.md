# 参照 gateway 沙箱运行结论

> 目的：为「对话记录对比验收」建立可复现的运行环境。
> 原则：**不碰官方数据目录，不修改 app 包内文件**。

## 一、能跑起来（无 v3）

```bash
GW="/Applications/MiniMax Design.app/Contents/Resources/gateway"
env -u ELECTRON_RUN_AS_NODE \
  HOME=/tmp/gw-sandbox/home \
  HILO_DATA_DIR=/tmp/gw-sandbox/data \
  node "$GW/dist/main.js"
```

启动成功，监听 **127.0.0.1:8001**（`HILO_PORT` 不生效，端口来自内部配置）。

**注意**：退出时它会尝试写 clean-shutdown marker 到 **app 包内**，报 `EPERM`。
在我们这里没写成功（好事），但这说明它默认会碰包内路径。

## 二、v3 需要三个前置条件

`dist/main.js` 里 `assertV3()`：

```js
assertV3() {
  if (this.current() !== "resource_v3"
      || process.env.HILO_GATEWAY_ROLE !== "workspace"
      || !process.env.WORKSPACE_DIR) {
    throw new ProjectKernelError(ProjectKernelErrorCode.PROJECT_V3_DISABLED);
  }
}
```

所以必须同时给：

```bash
HILO_GATEWAY_ROLE=workspace
WORKSPACE_DIR=/tmp/gw-sandbox/ws
HILO_PROJECT_ARCHITECTURE=resource_v3
```

**我们的 gateway 有一模一样的前置条件**（`workspace-project-architecture.service.ts:19`），
这条协议约束**已经一致**。

## 三、v3 路径的第一个硬障碍：原生 sqlite 绑定

只加三个 env 还不够，启动时会崩：

```
ERR_DLOPEN_FAILED
better-sqlite3 ... build/Release/better_sqlite3.node
```

原因：**包内的 `better_sqlite3.node` 不是给本地 Node 编的**

```
file ... → Mach-O 64-bit bun
```

而 **Bun 也不支持 better-sqlite3**：

```
error: 'better-sqlite3' is not yet supported in Bun.
```

### 解法：在副本里重建

```bash
cp -R "$GW" /tmp/gw-copy          # 绝不改 app 包
cd /tmp/gw-copy
npm rebuild better-sqlite3        # 需要本机有编译工具链
file node_modules/better-sqlite3/build/Release/better_sqlite3.node
# → Mach-O 64-bit bundle arm64   ← 变成 Node 可加载
```

重建后 v3 就通了。

## 七、第 242 轮：打通认证，拿到 200，并修了 2 处协议差异

### 认证机制

`TokenService` 把凭据写在 **`os.tmpdir()`** 下（无 `HILO_RELEASE_REGION` / `HILO_RELEASE_CHANNEL` 时后缀为空）：

```
$TMPDIR/minimax-hub-gateway-token
$TMPDIR/minimax-hub-gateway-user-id
```

`scope()` 里：

```js
const subjectId = this.auth.getUserID();
if (!subjectId || !this.auth.getToken())
  throw new ProjectQueryError("UNAUTHENTICATED", "Sign in before accessing tasks", 401);
```

**所以只要写这两个文件就能通过认证。**

### 实测响应（参照 gateway）

| 请求 | 状态 | 响应体 |
|---|---|---|
| `GET /api/v3/tasks` | **200** | `{"items":[],"nextCursor":null,"coverage":{"status":"complete","reasons":[]}}` |
| `GET /api/v3/tasks/lookup?operation=x&requestId=y` | **422** | `{"error":{"code":"UNSUPPORTED_OPERATION","message":"Unsupported task operation","retryable":false}}` |
| `GET /api/v3/tasks/abc` | **404** | `{"error":{"code":"NOT_FOUND","message":"GenerationTask is not readable","retryable":false}}` |

### 修了 2 处差异

**（1）列表响应缺 `coverage`**

我们原来返回 `{ items, nextCursor }`，参照多一个：

```json
"coverage": { "status": "complete", "reasons": [] }
```

已在 `generate/tasks.ts` 的 `list()` 补上（并按 TS 类型标注 `reasons: string[]`）。

**（2）lookup 的错误码不对**

| | 参照 | 我们（改前） |
|---|---|---|
| code | `UNSUPPORTED_OPERATION` | `INVALID_ARGUMENT` |
| message | `Unsupported task operation` | `Unknown task operation` |
| status | `422` | `400` |

已改成与参照一致。

### 已确认一致的部分

```
GET /api/v3/tasks/abc → 404 {"code":"NOT_FOUND","message":"GenerationTask is not readable"}
```

两边的 code、message、status **完全一致**。

### 这说明对比验收是有效的

**一个端点、三次请求，就找出 2 处协议差异**，其中 `coverage` 缺失会导致客户端
拿不到分页覆盖度。这类差异靠静态审计和 UI 门禁都发现不了。

### 下一步

1. 把这三条请求固化成对比脚本，接进门禁（用户方案的硬规则 5）；
2. 继续覆盖 `task_subscribe`（WS）与 `POST /api/v3/tasks`（提交）。

## 八、第 245 轮：`task_subscribe` 的完整契约（WS）

### 消息形状

```jsonc
// 订阅
{ "type": "task_subscribe",
  "subscriptionId": "...",          // 必填，非空，≤128
  "taskIds": ["..."],               // 可选，≤100 个，每个非空 ≤512
  "includeProjectChanges": true }   // 可选，布尔

// 退订
{ "type": "task_unsubscribe", "subscriptionId": "..." }
```

### 校验顺序（逐条实测自 dist/main.js 的 `TaskSubscriptions.handle`）

| # | 条件 | 失败响应 |
|---|---|---|
| 1 | `subscriptionId` 非空字符串且 ≤128 | `INVALID_ARGUMENT` "Invalid subscriptionId" |
| 2 | `architecture.assertV3()` | `PROJECT_V3_DISABLED` |
| 3 | 已登录（有 userID 与 token） | `UNAUTHENTICATED` "Sign in before subscribing" 409→401 |
| 4 | `taskIds` 可选；≤100 个、每个非空 ≤512 | `INVALID_ARGUMENT` "taskIds must contain at most 100 identifiers" |
| 5 | `includeProjectChanges` 可选布尔 | `INVALID_ARGUMENT` "includeProjectChanges must be boolean" |
| 6 | 同一 `subscriptionId` 参数变了 | `SUBSCRIPTION_ID_REUSED` "Subscription parameters have changed"（409） |
| 7 | 每客户端订阅数 ≥20 | `RATE_LIMITED` "Too many task subscriptions"（429） |

**退订**回一条：

```json
{ "type": "task_subscription_closed", "subscriptionId": "..." }
```

未装配 TaskSubscriptions 时（`tasks` 为 null），回：

```
GATEWAY_INTERNAL "Task subscriptions are unavailable"（retryable: true）
```

### 依赖

`TaskSubscriptions` 需要 `TaskStore`（`store.onChanged`）+ `TokenService`（`auth.getUserID/getToken/getGroupID`）
+ `ProjectChangeService`（`changes.onChanged`）。

### 我们这边的情况

```
app/gateway/src/chat/app.gateway.ts   74 行
  只处理 msg.type === "ping"
  没有 task_subscribe / task_unsubscribe / editor_subscribe / 聊天
grep task_subscribe app/gateway/src → 0 处
```

**这正是你在第 193 轮指出的问题**：参照实现了 `task_subscribe`，
而它依赖的 `TaskStore` / `TokenService` / `ProjectChangeService` 我们一个都没有。

### 这意味着

`task_subscribe` 不是一个端点的问题，而是**三个服务 + 一个订阅管理器**：

```
TaskSubscriptions  ← TaskStore（任务变更通知）
                   ← TokenService（身份）
                   ← ProjectChangeService（工程变更通知）
```

参照里这几个服务都在 `project-kernel/tasks/` 那 68 个模块里。

### 下一步（可执行）

1. 先做 `TokenService`（最小：从 `$TMPDIR/minimax-hub-gateway-{token,user-id}` 读，我们已有该路径逻辑）；
2. 再做 `TaskStore.onChanged`（我们的 tasks 表已有，加一个 emitter 即可）；
3. 最后做 `TaskSubscriptions`（按上表逐条实现，7 条校验 + closed 回执）。
