# 像素护栏：修正记录（第 2036 轮）

## 问题（由审阅指出，属实）

1. **护栏是 4.0.0 时代的旧值**：`residual-budget.json` 的 `_source` 还写着
   `~/ov-golden-ref（35 屏）`，而现行基线是 `~/ov-golden-4.0.3-clean`（4.0.3，37 屏）。
2. **两个方向都错**：
   - **太紧**（16 屏 `over`）：例如 `home-skill` 护栏 0.57% 而实测 6.25%、
     `home` 护栏 9.24% 而实测 14.72%
   - **太松**（20 屏比实测宽 0.5pp 以上）：例如 `workflows` 护栏 11.27% 而实测 0.33%、
     `ws-code-editor` 3.01% 而实测 1.92%
3. **退出码恒为 1**：我此前每次运行都打印「退出码 1」，却直接报了 37/37，
   **没有追问退出码的来源**。这是本次最严重的疏漏。

### 机制澄清（与审阅意见略有不同）

`compare.mjs:2663` 的判定是：

```js
const pixelDiffNonAA =
  budgetStatus === "invalid" ? false
  : typeof budgeted === "number" ? budgetVerdict === "over"   // ← 有护栏时只看 over
  : d.nonAARatio !== 0;                                        // ← 无护栏时任何差都失败
const pageFailed = pixelDiffNonAA || newErrors.length > 0 || unregisteredDiffCount > 0;
```

**所以 `budgetVerdict` 是参与判定的**（在「该屏有护栏」这一支里）。
退出码恒为 1 的直接原因是 **16 屏在旧护栏下判为 `over`**，而不是「有像素差就失败」。

**37 屏当前都有护栏**，因此走的是 `budgetVerdict === "over"` 这一支。

## 修正

   逐屏取两次实测非AA比值的**较大值**作为新 `guard`，并更新 `_source`。

   以及 `project-created` 那条已过时的排除理由（补上 `.hilo` 无会话表的实测结论）。

## 两次运行的稳定性（重要）

37 屏中 **35 屏在 0.02pp 容差内稳定**；只有两屏波动超容差：

| 屏 | 两次实测 | Δ |
|---|---|---|
| `changelog` | 0.530% vs 0.329% | **0.201pp** |
| `workflows` | 0.416% vs 0.334% | **0.082pp** |

这两屏的 `guard` 取的是两次的较大值，因此**只能拦住大于该波动的退步**。
已在 `why` 字段里写明这一点。要收紧必须先查清它们的不稳定来源。

## 新增一条规则（采纳审阅建议）

> **护栏和基线必须同一批次生成；换了基线，护栏就要重新生成，
> 否则护栏本身就成了噪声。**

这条已并入 `docs/4.0.3-methodology.md`。
