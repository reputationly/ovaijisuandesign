# 像素护栏：修正记录（第 2036 轮）

## 问题（由审阅指出，属实）

1. **护栏是 4.0.0 时代的旧值**：`residual-budget.json` 的 `_source` 还写着
   `~/ov-golden-ref（35 屏）`，而现行基线是 `~/ov-golden-4.0.3-clean`（4.0.3，37 屏）。
2. **两个方向都错**：
   - **太紧**（16 屏 `over`）：例如 `home-skill` 护栏 0.57% 而实测 6.25%、
     `home` 护栏 9.24% 而实测 14.72%
   - **太松**（20 屏比实测宽 0.5pp 以上）：例如 `workflows` 护栏 11.27% 而实测 0.33%、
     `ws-code-editor` 3.01% 而实测 1.92%
3. **退出码恒为 1**：我此前每次运行都打印「退出码 1」，却直接报了 37/37，
   **没有追问退出码的来源**。这是本次最严重的疏漏。

### 机制澄清（与审阅意见略有不同）

`compare.mjs:2663` 的判定是：

```js
const pixelDiffNonAA =
  budgetStatus === "invalid" ? false
  : typeof budgeted === "number" ? budgetVerdict === "over"   // ← 有护栏时只看 over
  : d.nonAARatio !== 0;                                        // ← 无护栏时任何差都失败
const pageFailed = pixelDiffNonAA || newErrors.length > 0 || unregisteredDiffCount > 0;
```

**所以 `budgetVerdict` 是参与判定的**（在「该屏有护栏」这一支里）。
退出码恒为 1 的直接原因是 **16 屏在旧护栏下判为 `over`**，而不是「有像素差就失败」。

**37 屏当前都有护栏**，因此走的是 `budgetVerdict === "over"` 这一支。

## 修正

1. 用修好的门禁对 `~/ov-golden-4.0.3-clean` **连跑两次全量**（P / Q），
   逐屏取两次实测非AA比值的**较大值**作为新 `guard`，并更新 `_source`。
2. 顺带修掉 `compare.mjs:2486` 仍把 `~/ov-golden-ref` 称作「正式基线」的注释，
   以及 `project-created` 那条已过时的排除理由（补上 `.hilo` 无会话表的实测结论）。

## 第 2037 轮修正（审阅指出：那两屏不是"不稳定"，是**一次异常运行**）

### 审阅的核实

| 运行 | changelog | workflows |
|---|---|---|
| 04-47 | 0.3291% | 0.3335% |
| **06-58** | **0.5303%** | **0.4157%** |
| 07-15 | 0.3291% | 0.3335% |
| 07-33 | 0.3291% | 0.3335% |
| 07-54 | 0.3291% | 0.3335% |

**5 次里 4 次完全一致，只有 06-58 偏高。** 而我用「两次取较大值」，恰好把这次异常固化进了护栏。

**所以「这两屏不稳定」这个判断是错的** —— 是**一次**采集异常。

### 根因（推断，与审阅一致）

DOM 相同、像素整块不同（整片主内容区），**最可能是截图时页面还在过渡**：
淡入动画 / `MediaReveal` 渐显未结束。

**而 `stableShot` 原有的"连续两张一致"挡不住它**：
渲染进程被隐藏时节流会让动画**冻在中途**，两张截图"一致"地停在同一个中间帧。

### 修法（只改门禁）

在 `SETTLE` 里补两件事：

1. `await document.fonts.ready`
2. **把仍在运行的 CSS 动画/过渡推到终态**：
   `document.getAnimations().filter(a => a.playState === "running")` 逐个 `finish()`（失败则 `cancel()`），最多 3 轮

### 验证

| 检查 | 结果 |
|---|---|
| `changelog` / `workflows` 连跑 4 次 | 像素计数**四次完全相同**（20075/13171、20199/13259） |
| 修后全量 **连跑 3 次**（T/U/V） | 三次退出码均 **0**，**37 屏逐屏值完全一致**（0 屏不一致） |
| 用这三次一致值重生成全部护栏 | 32 屏值微调（因为动画终态改变了帧） |
| 最终验证全量 | **退出码 0 · 超护栏 0 · 未登记 0 · 平均 2.8727%** |

`changelog` 现为 **0.329081%**、`workflows` **0.333508%** —— 正是之前 4/5 次的稳定值。
`why` 里"波动超过容差"那段说明已删除。

### 仍存在的事实：13/37 屏会触发「重拍 8 次仍未稳定」

即使加了动画终态，仍有 13 屏在 8 次重拍内达不到"连续两张完全一致"。
**但三次全量结果完全一致** —— 说明这些抖动不影响最终取值。

**若要更彻底**：可提高重拍上限，或把 `STABLE_TOL` 从 0 放宽到极小容差
（目前是 0，即要求逐像素完全相同）。

### 新增方法论第九条（采纳审阅建议）

> **护栏只能用「已确认稳定」的运行来生成：至少 3 次结果一致才取值，
> 不能简单取两次里的较大值。**

## 第 2038 轮：三次一致也不够 —— 改用 5 次最大值

护栏取「三次一致的稳定值」后，**第 4 次运行仍有 3 屏超护栏**：

| 屏 | 阈值 | 实测 |
|---|---|---|
| `home` | 14.7212% | **14.7756%** |
| `home-skill-inspiration` | 14.7405% | **14.7817%** |
| `home-skill` | 6.2490% | **6.2836%** |

用 5 次全量（T/U/V/W/X）统计跨运行波动：

| 屏 | 波动 |
|---|---|
| `home` | **0.0544pp** |
| `home-skill-inspiration` | **0.0412pp** |
| `home-skill` | **0.0346pp** |
| 其余 34 屏 | ≤ 0.0122pp |

**噪声源已知**：首页 `showcase-assets` 图片「挂载后又被卸载」的生命周期
（第 243 轮查证，见 `4.0.3-showcase-assets-finding.md`）。

### 处置

- `guard` = **5 次全量逐屏最大值**
- `_source` 改为「连跑 5 次全量取最大值」
- 那 3 屏的 `why` 写明实测噪声值与**代价**：
  **小于该噪声的退步拦不住；要收紧需先消除图片生命周期抖动**

### 验证

```
全量 37 屏：退出码 0 · 超护栏 0 · 未登记 0 · 平均 2.8765%
```

### 对第九条规则的补充

**「3 次一致」仍然不够** —— 如果一个屏是**间歇性**抖动（大多数轮次一致、偶发偏差），
三次可能恰好都落在稳定值上。

**更稳的做法**：跑 5 次，`guard = max`，并把实测波动写进 `why`。
**只有当某屏波动 ≈ 0 时，「取稳定值」才等价于「取最大值」且不留松量。**
