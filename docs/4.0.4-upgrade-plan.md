## 一、第一件事：把补丁层恢复出来，用在 v3 工作台上

### 目录

```
app/official-ui/
  build.mjs        补丁引擎（从 993ca82e 取回，补两处）
  patches.mjs      补丁表（新建，先只有品牌）
  assets/          自有资源（蒜狸形象、品牌字体）
```

### 补丁引擎要补的两处

1. **打完补丁后重生成 `bundle-manifest.json`**
   现有 `stage-v3-bundle.mjs` 是 `cpSync` 后直接结束；需要改成：
   `cpSync → applyPatches(DEST) → regenerateManifest(DEST)`。
   **否则 `bundle.ts` 的 sha256 校验会拒绝加载。**
2. **文件按前缀匹配 + 命中数断言**
   旧版的 `file` 就是前缀（`assets/index-`），`count` 不符即 `process.exit(1)`。
   这条正好实现你要的"升级时由构建失败提醒"。

### 第一批补丁：只做品牌

按可长期稳定的字面量定位，**不用变量名**：

| 类别 | 定位方式 | 备注 |
|---|---|---|
| i18n 资源里的产品名 | 区间限定到 `const en…= {` / `const zh = {` 两段内整体替换 | 沿用 993ca82e 的 `EN_I18N`/`ZH_I18N` 区间，避免误伤模型 id、存储键 |
| 页面标题 `<title>` | `v3/index.html` 里的字面量 | 现在是 `MiniMax Design V3` |
| 写死的品牌串 | `"MiniMax Design"` / `"MiniMax"` / `"海螺AI"` 等字面量 | **每条必须写 `count`** |
| 自有资源注入 | `ASSETS` + `index.html` 注入 `<link>`/`<style>` | 沿用旧版做法 |

**执行顺序**：先只加 `<title>` 一条，跑通「打补丁 → 重生成 manifest → 应用能加载」这条链路；
再按类别逐组加，每加一组跑一次构建。

**先不做的**：那 65 处里有多少是界面上可见的，我还没查。
**建议第一轮只替换确定可见的**（标题、i18n 品牌名、logo 相关），其余逐条确认后再加。

## 二、第二件事：建 upstream 分支

### 现状

当前在 `wip/4.0.0-restore`，参照的 chunk 内容（`canvas-v3/`、`export-engine/` 等）和我们
自己的改动**混在同一个分支的历史里**，升级时没法做三方合并。

### 目标结构

**不要每个版本开一条分支，用一条 `upstream` 分支 + 版本标签：**

```
upstream   提交① 4.0.3 的生成内容   → 标签 upstream-4.0.3
           提交② 4.0.4 的生成内容   → 标签 upstream-4.0.4
              │
product    在 product 上执行：
             git merge --allow-unrelated-histories -s ours upstream
           （只记录合并基础，不改 product 任何文件）
              │
              ▼  以后升级：upstream 提交新版本 → 再 merge 进 product，
                 git 以「上一个版本的生成内容」为基础做三方合并
```

- **product 直接从现在的 `wip/4.0.0-restore` 开出**，不需要把已有改动重新提交一遍；
- 补丁表与产品改动都在 product 上。

### 落地步骤

1. **先只做 v3 这一块**（范围最小、最容易验证）：
   - upstream 分支只放**从参照生成、没被我们改过**的内容：v3 压缩包、锁文件、装配脚本；
   - **补丁表（`app/official-ui/`）不放 upstream，放 product** —— 它是我们的改动。
     放进 upstream 会破坏「两边都改过才冲突」这个判断。
2. **整块 chunk 部分**（`canvas-area-v3.js` 等）：把这些文件在 `upstream/4.0.4` 上
   从 4.0.4 重新生成一次提交；
3. `product` 分支从 `upstream/4.0.4` 拉出，把我们的改动重放上去；
4. 以后升级：`upstream/4.0.x` → merge 进 `product`，冲突即"两边都改过"。

### 风险与前置

- **必须先确认哪些文件属于"整块 chunk 镜像"**。我建议先出一张清单
  （文件名 + 是否纯镜像 + 我们的改动行数），否则 upstream 分支的边界不清。
- 这一步会改写分支结构，**建议在冻结已完成（本轮已做）之后、动产品代码之前做**。

## 四、顺带：去掉脚本里写死的版本号

与三件事一起做，理由：现在同时有 4.0.3/4.0.4 两个版本，写死的路径很容易拿错比。

- 24 个脚本写死 `reference/4.0.x` 路径 → 统一 `--from` / `--to` 或 `OV_REF_*` 环境变量；
- 23 个写死带哈希的 bundle 文件名 → 从冻结目录的 `renderer/index.html` 里读；
- `check-constants.mjs` 的 `REF_BUNDLES` 手工表 → 改为自动推导；
- 加 `scripts/refdiff/upgrade.mjs --from 4.0.3 --to 4.0.4`：串起冻结校验、delta、toplevel 差异，
  **只读、只出报告**。

## 五、建议的动手顺序

1. **去写死版本号 + `upgrade.mjs`**（只读，风险最低，且是后面所有步骤的地基）
2. **补丁层恢复 + 首批品牌补丁**（需要改 `stage-v3-bundle.mjs`，要跑一次桌面构建验证）
3. **产品改动清单**（纯文档，可随时做）
4. **upstream 分支**（改仓库结构，放最后；动手前需要先确认 v3 产物是否入库）

## 六、需要你确认的三点

1. **v3 产物是否入库**？不入库的话 upstream 分支对 v3 只能管"装配脚本 + 补丁表"。
2. **品牌补丁第一批的范围**：只做标题 + i18n 品牌名，还是连 logo/字标一起（后者要带资源文件）？
3. **upstream 分支的命名与边界**：`upstream/4.0.4` 是否需要同时覆盖主界面 chunk 与 v3，
   还是先只做 v3、主界面 chunk 后续再迁？
