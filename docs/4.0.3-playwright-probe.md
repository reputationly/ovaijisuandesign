# Playwright 诊断验证（第 2037 轮）

脚本：`.probe/pw/probe.mjs`（依赖 `playwright-core@1.64.1`，装在 `.probe/pw`，**不下载浏览器**，
用仓库自带的 Electron 可执行文件）。

**只跑 skills-connectors 与 home 两屏，不替换现有门禁。**

## 三个问题的答案

### 1) trace/HAR 能否看到状态码与响应内容？—— **能**

```
/api/plugins → {"status":200,"bytes":14,"head":"{\"plugins\":[]}"}
```

**而且这一条直接给出了 `skills-connectors` 的解释**：接口返回 **200 但内容为空**
（`{"plugins":[]}`）。结合参照那屏是失败态（`page-state-error-retry`），
可以确定两侧停在不同的终止状态：我们成功但空，参照失败。

**另外抓到一次时序问题**：某次首屏 `/api/plugins` 拿到
`net::ERR_CONNECTION_REFUSED`（网关端口尚未监听），重试后才是 200。
**这正是"网关就绪前就发请求"的实证**，也是全量与单屏结果会漂移的一个来源。

### 2) `route` 能否拦下 `showcase-assets`？—— **能，命中 22 次**

**结论：这些请求确实来自本页。** 现有门禁用 `Fetch` + `setBlockedURLs` 拦不住，
是**门禁侧的缺陷**，不是"请求来自别处"。

### 3) 同一屏跑两次，请求序列差异能否定位状态污染？—— **能，而且很干净**

```
run1 请求数: 70   run2: 68
差异只在 showcase-assets/<hash> 的资源名上（按 sitemap 随机，每次不同）
结构上没有差异
```

**也就是说：trace 能自动把"资源名这类噪声"和"真正的结构差异"分开** ——
这恰好是现有门禁最缺的能力。

## 建议（按优先级）

1. **先接 trace**（不改现有截图/比较逻辑）：每屏一份 trace，
   出错时可回看 DOM 快照 + 带状态码的网络 + 控制台。
2. **用 `route` 替换现有的 `Fetch`/`setBlockedURLs`** 来做请求拦截与响应伪造 ——
   它已被证明能拦住 showcase-assets。
3. **把"网关就绪检查"加到每屏导航之前**（等端口监听成功），
   消除 `ERR_CONNECTION_REFUSED` 这类时序噪声。
4. HAR 可后置：trace 已覆盖状态码与响应体，HAR 主要是为了跨运行 diff，
   而 run1/run2 的差异目前看只有资源名。

**不建议整套迁移**：现有门禁的截图、遮罩、集合判据是这一百多轮的核心资产，
Playwright 只补"诊断可观测性"这一层即可。
