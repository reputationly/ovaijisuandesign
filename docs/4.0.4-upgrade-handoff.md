## 1. 规则（在 v3 交接文档第 1 节基础上补充）

1. **不能半升级**：v3 运行时、v3-workbench preload、protocol、gateway、MCP 必须一起切到 4.0.4。
   `scripts/stage-v3-bundle.mjs` 会检查锁文件版本 = `scripts/reference-version.json`，不一致就构建失败 —— **不要绕开这条检查**，
   最后一步再一起改版本号。
2. **4.0.3 的基线和护栏不覆盖**：新基线录进新目录；护栏换成 4.0.4 同批 5 次的值（旧值留在 git 历史里）。
3. **每条「跟 / 不跟」都要有依据**：跟的写落点，不跟的写原因（范围外 / 依赖云端 / 有意差异），写进升级报告。
4. **工具提议不可全信**：`apply-delta.mjs` 的「可直接套用」要逐条核对新旧是否同一实体（看模块邻居，`$n` 后缀和通用名不可信）；
   `--apply` 只用于「上游改了、我们没动」且核对过的条目；冲突一律人工处理。
5. 新功能如果需要调用对方云端（账号、计费、云端发布、对方域名），**不接**，界面保持与参照在「未登录 / 不可用」时一样的表现，并登记。

## 4. 怎么做（分阶段，每阶段单独提交、单独验收）

### 阶段 0：补全差异报告（只读）

1. 复跑 `node scripts/refdiff/upgrade.mjs --from 4.0.3 --to 4.0.4`，确认第一版报告的数字可复现。
2. **gateway**：用冻结的 4.0.4 重新生成路由台账（`scripts/extract-gateway-routes.py`，默认读安装目录，
   要让它读 `.probe/reference/4.0.4` 的 gateway —— 如果脚本不支持，给它加一个参数，**只改工具**）；
   再做 4.0.3 ↔ 4.0.4 的 gateway 模块级对比（上一轮的口径：改动 / 新增 / 删除的模块）。
   只把 **4.0.4 新增或改动** 的路由和模块拿出来逐条判断，已经在 4.0.0 时定性过的不再重复。
3. **MCP**：用冻结的 4.0.4 `sidecar/mcp-tools-v3` 生成参照快照：
   `OVMCP_ENTRY=<4.0.4 的 mcp-tools-v3 入口> OVMCP_OUT=/tmp/ref-tools-4.0.4.json OVMCP_SOURCE=4.0.4 OVMCP_SKIP_COMPARE=1 node scripts/mcp-compare/probe.mjs`
   （先读 `probe.mjs` 头注释确认变量），与现有 `reference-tools.json` 做 `deep-schema-diff.mjs`，列出变了的工具。
   **这一步不要覆盖 `reference-tools.json`**，阶段 3 再换。
4. **preload / 主进程**：`out/preload/*.{cjs,mjs}`、`out/main/index.js` 逐文件对比；列出 IPC 频道和 `contextBridge` 暴露成员的增减。
5. **v3 运行时**：按 chunk 基名配对 4.0.3 / 4.0.4 的 `renderer/v3`，列出改动的 chunk 和界面 id 的增减。
6. **agent 配置、技能文本**：`sidecar/agent-profiles` 等目录做文本对比。
7. 把以上结果写成 `docs/4.0.4-upgrade-report.md` 的第二版，加上第 3 节表格的结论。**把工具补进 `upgrade.mjs`**，让下次一条命令能出全部。

**阶段 0 验收**：报告里每个面都有数字和证据路径；第 3 节每一项有结论；需要负责人定的列在最前面。**交给负责人确认后再进阶段 1。**

### 阶段 1：后端与协议（gateway、protocol、MCP、主进程、preload）

1. gateway：逐个移植要跟的改动和新增模块到 `app/gateway/src`（TS，带测试）。参照 gateway 未压缩、带函数名，照着读。
2. protocol：`app/packages/protocol` 对齐 4.0.4（音乐参数、`code-project`、`site-preview` 等）。协议有多份副本的，三份一起改。
3. MCP：阶段 0 的参照快照换进 `reference-tools.json`，跑 `gen-v3-schemas.mjs` 重新生成，`app/mcp-tools` 的测试 25/25 逐字段一致
   （工具数如果变了，以 4.0.4 为准）。
4. 主进程 / preload：`app/desktop/src` 对齐（v3-workbench preload 的音乐工具、`code-project`、`site-preview`）。
5. agent 配置、技能文本：照搬后做品牌替换（规则见 `ov-changes.md` #1）。

**阶段 1 验收**：
- `pnpm turbo run build typecheck test` 全绿（gateway e2e 如果偶发失败，先 `--no-file-parallelism` 串行跑定位，别重跑了事）；
- `node scripts/gateway-compare/compare.mjs` 与重放：参照夹具要换成 4.0.4 的（怎么录见脚本头注释），真差异为 0 或逐条登记；
- MCP 快照对比 0 差异；
- 此时 v3 仍是 4.0.3 产物、版本号仍是 4.0.3，**全量 37 屏和 v3 七屏门禁对 4.0.3 基线不退步**（后端改动不应改变 4.0.3 界面的行为；变了要解释）。

### 阶段 2：主界面（`app/renderer/src`）

1. `node scripts/refdiff/apply-delta.mjs --old-src <4.0.3 主体 bundle> --new-src <4.0.4 主体 bundle>` 先 dry-run。
   **4.0.4 的主体是 `mermaid-GHXKKRXX-*.js`，不是 `index-*.js`**；用 `lib/refs.mjs` 解析，不要手写文件名。
   `scripts/v3preload/` 下还有 8 个脚本写死了 4.0.0/4.0.3 的文件名，用到哪个改哪个（改成走 `refs.mjs`）。
2. 逐条核对后套用「上游改了、我们没动」的；冲突人工合并；新增语句按第 3 节的范围判断决定落点；删除的先查引用再删。
3. 整块复制的 chunk（`canvas-v3/canvas-area-v3.js`、`export-engine/*` 等）：对应的参照 chunk 4.0.3 ↔ 4.0.4 的差异按块搬过来。

5. i18n：新增 40 个键照搬（中英文），删掉的 9 个确认无引用后删。

**阶段 2 验收**：静态检查全部不变差（`audit-v3` 全部通过）；构建通过；此时还没换基线，门禁对 4.0.3 基线会出现**预期内**的差异 ——

## 7. 本任务特有的坑

- **主体 bundle 改名**：4.0.4 的 `index-*.js` 只是引导脚本，按「`index-*.js` 就是主 bundle」去比会得到「全部只在旧版有」这种荒谬结果。
  所有工具都要走 `scripts/refdiff/lib/refs.mjs`。
- **半升级**：只换 v3 产物、不换 preload / protocol，是这个仓库真实发生过的错误（提交 `c71c3264` 修的）。版本一致性检查就是为此加的。
- **gateway 台账口径**：`docs/gateway-api.md` 是 4.0.0 的，拿它比会得出「gateway 没变」的假结论。
- **旧欠账混进来**：4.0.0 → 4.0.3 没合完的语句，在 4.0.3 → 4.0.4 的三方合并里会表现为冲突。分清「这是 4.0.4 的改动」还是「这是上一轮没合的」，
  后者单独列，不要顺手处理成半成品。
- **护栏和基线同批**：换基线后，旧护栏全部作废。
