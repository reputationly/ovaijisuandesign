## 实测记录（第 158~162 轮，三次尝试都不如不挂）

| 版本 | home 像素 | 未登记差异 |
|---|---|---|
| **不挂托盘（当前状态）** | **14.7212%** | 4 |
| 挂在 fragment 末尾 | 14.7404% | 3 |
| footerSlot 在根 div 末尾 | 17.7051% | 3 |
| footerSlot 在 actions bar 之前 | 17.7024% | 3 |

### 关键结论：**不能只补元素，必须同时改变卡片尺寸关系**

后两个版本只差 0.003pp —— 位置几乎不影响，**说明主因是托盘带来的 42px 高度**。

参照里托盘是卡片的一部分，所以**参照的卡片本身就比我们高 42px**，
下方内容（创作灵感标签、卡片网格）的位置也随之不同。

我们的卡片高度由 `MessageInput` 的内容决定，`message-input-surface` 是调用方
通过 `className` 传进去的 —— 外部无法既插内容又保持卡片高度关系。

### 因此正确的实施顺序应当是

1. 先量出参照首页 composer 卡片的**总高度**，以及下方内容相对它的偏移
2. 把这两条尺寸关系写进 `MessageInputBase`（或 home 的外层容器）
3. **最后**才插托盘 —— 否则每插一次都会把下方推低 42px，差异反而变大

### 已实现、可复用的部分（不要重做）

- `MessageInputBase` 已支持 `footerSlot`（插在 actions bar 之前），当前无人使用、无副作用
- `HomeProjectFolderIcon` 已补（`ClosedFolderIcon` 的封装）
- `HomeProjectPicker` 组件已存在（`home/prompt-picker.jsx:17`），触发按钮已有 `home-project-btn`
- 托盘容器的完整类名见本文档上一节

### 方法论

**"把参照的元素补上"不等于"像素会更接近"。**
当元素参与容器尺寸时，只补元素而不调整尺寸关系会让差异变大。
判断方法：补上后若差异明显变大，先怀疑尺寸关系没跟着改，而不是怀疑元素本身。
